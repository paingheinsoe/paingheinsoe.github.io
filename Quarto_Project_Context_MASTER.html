Quarto Portfolio & Learning Hub — Master Project Context

Use this document as the handoff context whenever continuing this website with ChatGPT, Claude, or another coding assistant. Treat the website as an existing project that must be developed incrementally, not rebuilt from scratch.

1. Project identity

This is Paing Hein Soe’s Quarto-based Portfolio & Learning Hub.

Local Windows project root:

D:\Portfolio_Drive\Quarto_website

Primary working environment: - Quarto website project - Visual Studio Code - Windows PowerShell - HTML output generated by Quarto - Custom CSS in styles.css - Small custom JavaScript for article counts - GitHub / GitHub Pages is the intended publishing path, but the current Git/repository/publishing state must be checked rather than assumed.

2. Purpose of the website

The site has two related purposes.

A. Professional portfolio

The portfolio should present professional background, experience, research, selected projects, publications, and technical skills with enough depth to show the actual work behind a resume. It should not simply duplicate a CV. Project pages should emphasize the problem, role, data/methods, analysis, results, visuals, and what was learned or contributed.

B. Learning hub

The learning hub is a place to publish useful articles based on topics being learned, used, tested, or applied. The goal is not to produce generic blog content. Articles should help a reader understand a topic or reproduce a workflow.

The main topic areas are: 1. Energy & Climate 2. AI & Agents 3. Data Analytics 4. Programming & Technology

The overall site should make sense to both professional visitors (employers, collaborators, researchers) and readers who come for practical learning material.

3. Core editorial principles

These rules are important and should be preserved in every new article or revision.

  • Do not write in a generic AI-generated article style.
  • Prefer a natural, direct, thoughtful, technically accurate voice.
  • Avoid inflated introductions, marketing language, repetitive encouragement, filler, and predictable phrases such as “in today’s rapidly evolving world.”
  • Do not make the author sound like an expert on something merely because an AI can explain it. Where appropriate, write from the perspective of someone learning, testing, applying, or documenting the workflow.
  • Explain not only what to do, but why the step matters, what the reader should expect to see, and what can go wrong.
  • Use exact commands, filenames, paths, screenshots, tables, diagrams, code snippets, or checkpoints when they genuinely make the workflow easier to understand.
  • Keep technical explanations accessible without becoming shallow.
  • Use practical examples and real project context whenever possible.
  • Be transparent about assumptions, limitations, uncertainty, and sourced facts.
  • For current factual claims, software behavior, or external technical guidance, verify against authoritative sources when needed.
  • Visuals should add information or reduce confusion, not act as decorative filler.

A good article often includes: - a clear explanation of the topic; - an organized workflow or sequence; - practical examples or applications; - screenshots/figures where useful; - checkpoints showing what should happen; - common questions, pitfalls, or troubleshooting notes; - a short, natural conclusion or next step.

Do not force every article into an identical template. The structure should serve the topic.

5. Current design direction

The current source uses a restrained, professional visual system rather than a flashy template.

Key colors from styles.css: - page background: #f7f4ef - surface: #ffffff - soft surface: #eee9e3 - charcoal: #252321 - secondary charcoal: #373330 - primary text: #252321 - secondary text: #68615b - warm rust/chili accent: #a64232 - dark rust: #7f3025 - soft rust: #e4c2ba - border: #ddd5cc - main content width: about 1180px

The navbar and footer use charcoal. The rest of the site uses warm off-white/cream backgrounds, white cards, restrained borders/shadows, and rust accents.

The homepage currently uses a text-focused welcome panel. Earlier versions explored a dark hero, split image hero, gradient hero, and slider concepts, but those are not the current implementation. Do not reintroduce them unless specifically requested.

The current homepage flow is approximately: 1. Portfolio & Learning Hub welcome 2. Latest/recent articles (automatic Quarto listing, max 3) 3. Four topic-area cards 4. “Clear, Organized, and Easy to Follow” learning-hub explanation 5. Portfolio teaser / link

Design priorities: - readability first; - clear hierarchy; - generous whitespace; - professional rather than trendy; - consistent cards and spacing; - useful visual support; - responsive behavior on smaller screens.

6. Current Quarto configuration

_quarto.yml defines a website with the navigation above, search, LinkedIn/GitHub links, a dark footer, the Cosmo/theme setup, styles.css, smooth scrolling, external links opening in a new window, and article-counts.html included after the page body.

Do not change global configuration casually. Check how a change affects all pages before modifying _quarto.yml or global CSS.

7. Article/listing architecture

articles.qmd lists articles/**/*.qmd, newest first, in a 3-column grid. It currently uses a page size of 9 and a filter UI.

Each topic page lists the .qmd files inside its corresponding article folder.

The homepage also lists recent articles automatically and shows at most three.

article-counts.js scans rendered article cards and fills the total/category counts shown on articles.qmd. This was added during iterative development. If the article collection grows beyond the listing page size or pagination behavior changes, re-check whether these counts still represent the full collection rather than only rendered cards.

8. Current substantive article

The first real article is:

articles/programming-technology/getting-started-with-quarto.qmd

Title: Getting Started with Quarto

It is a beginner-oriented Windows guide that explains: - what Quarto, VS Code, and PowerShell each do; - installing Quarto and VS Code; - creating the workspace; - moving to the project directory with PowerShell; - creating a Quarto website; - previewing it locally; - understanding localhost; - editing index.qmd and seeing Quarto rebuild; - screenshots and checkpoints throughout.

The article intentionally explains the reasoning behind the steps instead of giving commands without context.

Its image assets are under:

images/quarto/

The article refers to them from its nested folder using paths such as:

../../images/quarto/download-vscode.png

When editing this article, preserve its practical teaching purpose but refine wording that feels repetitive or overly template-like. Repeated phrases such as “At this stage,” “Great,” “Congratulations,” or formulaic callouts should be used sparingly so the writing remains human and natural.

11. Development rules for an AI coding assistant

When helping with this project:

  • Inspect the current file before proposing edits. Do not overwrite working architecture based on a generic Quarto template.
  • Treat index.qmd, _quarto.yml, styles.css, topic pages, and article files as established source files.
  • Never edit _site/ or .quarto/ as the solution; they are generated output/cache.
  • Make one logical change at a time where possible and explain what file is changing and why.
  • Preserve existing navigation, visual system, article directory structure, and relative image paths unless there is a specific reason to change them.
  • Give exact Windows/PowerShell commands when a local command is needed.
  • Avoid asking for files already present in the supplied project. Ask only for genuinely missing information.
  • If proposing substantial CSS or _quarto.yml changes, consider homepage, articles page, topic pages, article pages, and mobile behavior together.
  • Do not invent professional project results, publications, dates, affiliations, metrics, or skills. Ask for source material if needed.
  • For portfolio content, distinguish clearly between what belongs on a resume and what deserves deeper portfolio evidence.
  • For article content, prioritize accuracy and teaching value over SEO-style filler.
  • Where the current code is imperfect, fix it incrementally rather than starting over.
  • When debugging, first identify whether the issue is Quarto/YAML, file paths, listing behavior, CSS layout, JS, or generated-cache state.
  • Prefer quarto preview for local development and verify changes in the browser.

12. Useful local diagnostic commands

From Windows PowerShell:

cd D:\Portfolio_Drive\Quarto_website
quarto check
quarto preview

For Git status, if Git is installed:

git status
git branch --show-current
git remote -v

Do not assume the project is already a Git repository. Report the actual output first.

13. How to start a new AI conversation

At the beginning of a new conversation, provide this context document and, when the code has changed substantially, the latest ZIP of Quarto_website.

Then use a short instruction such as:

Read the attached Quarto Portfolio & Learning Hub project context first. Treat it as an existing project and preserve the established purpose, architecture, visual system, and editorial principles. Inspect the current source files before recommending code. Do not rebuild it from a generic template. My task for this session is: [INSERT CURRENT TASK]. Ask me only for information or files that are genuinely missing.

The project context should be updated whenever major architecture, navigation, design, editorial rules, or publishing workflow changes. It does not need to be rewritten for every small article edit.
